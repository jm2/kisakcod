# Roadmap review and expansion proposal

Review date: September 9, 2026 (America/Indiana/Indianapolis).

**Conclusion:** the existing plan covers most large engineering categories, but it is not yet a comprehensive, dependable delivery backlog. Its strongest work is ABI separation, bounded asset conversion, explicit ownership, and preserving the Windows x86 baseline. Its weakest points are production integration evidence, compatibility acceptance tests, actionable subdivision of the remaining loader work, and reconciliation between historical documentation and the Gas City queue. The multi-platform direction is sound; the current sequencing is unnecessarily serial and several platform assumptions need experiments before they can support estimates.

The user authorized the backlog expansion: [fork issue #122](https://github.com/jm2/kisakcod/issues/122) is the mandatory original-binary network parent, and A01–A15 below link to created fork issues #123–#137. Issue creation does not mark a milestone complete or reassign a live Gas City worker; reconcile these issues with the remote bead graph before scheduling.

The committed product scope remains **MP client and headless dedicated server**. SP is deferred in [PORTING.md](PORTING.md); existing SP baseline protection and already-landed save converters should be preserved, but full native SP delivery is not added to this proposal's critical path.

**Mandatory original-binary network requirement:** follow [NETWORK_COMPATIBILITY.md](NETWORK_COMPATIBILITY.md). [Issue #122](https://github.com/jm2/kisakcod/issues/122) tracks this unchecked release gate. All five requested targets must interoperate perfectly in both directions with the original, unmodified commercial 1.7 and original, unmodified Steam 1.8 client/server references: native client → each original server, and each original client → native headless server. Steam 1.8 must not be confused with community CoD4x 1.8. Exact executable/content hashes and observed protocol details are pending verification; no original-reference cell has passed. Fork protocol-1 sessions, CoD4x, guessed version constants and patched retail binaries are not substitutes. Preserve valid retail packet bytes and semantics without imposing the fork's added GUID arguments or Steam-ticket authentication convention on original peers. Optional incompatible modernization must remain separate from this required path.

## What is already covered well

Keep the Disk32/native-runtime split, retail asset and wire compatibility, explicit ABI assertions, high-address testing, generation-checked ownership, and the distinction between portable utility jobs and delivered engines. The plan already identifies Miles/Bink replacement, old zlib, headless separation, renderer semantics, physical ARM runners, signing, provenance, fuzzing and sanitizer requirements. Reopening those as wholly new discoveries would duplicate substantial work.

The atomic seven-site loader enrollment requirement addresses a real shared ownership contract. Splitting delivery into smaller capabilities must not turn that enrollment into an unsafe partial cutover. Likewise, changing a CMake gate or adding a preset does not fix the runtime layout that gate protects.

The dashboard's **0/5 production targets** is the useful delivery measure. The historical 84% overall and per-platform effort estimates have no reproducible denominator; they have been removed from the current dashboard and should not be used to forecast remaining calendar time: client rendering, shader conversion, audio, and complete loader integration still contain large unknowns.

## Is the multi-platform strategy optimal?

**Keep its architectural destination; revise its critical path and evidence model.** The existing Disk32 conversion is necessary for the project's retail-content goal. Replacing it with rebaked native-width assets would change that goal. The plan should also retain a working x86 compatibility target while conversions land.

The highest-value change is to separate native server delivery from full client completion. The reviewed [PORTING.md:1376](https://github.com/jm2/kisakcod/blob/5f29e810df88f0be323fccdc7d597c58e0d59f17/docs/PORTING.md#L1376) bundled Win64 link, script-heavy save/load, complete fast-file conversion, graphics and audio into successive large milestones. That postpones integration feedback. A native headless server does not need the complete client renderer, Bink, audio output, or SP save support. It still needs every asset and runtime family reachable by its supported maps; a null backend is not permission to skip structurally required parsing.

Use a Win64 headless build as an internal ABI reference if it reaches a real map sooner, while preparing Linux amd64 engine composition in parallel. Original commercial 1.7 and Steam 1.8 remain the required network references. Deliver the Linux server once its supported content closure and sessions with both original clients pass; do not wait for a playable Win64 client. Keep unsupported capabilities explicitly gated; never enable all native64 modes because one test executable links. A complete platform still needs its native client validated against both original servers.

Run ARM simulation tests early, after the necessary runtime slices exist. macOS renderer feature experiments also belong early, even if its signed application remains a later deliverable. Otherwise an expensive Linux Vulkan implementation can depend on features that the final Apple backend cannot provide. There is no need to make every OS wait for the previous full client.

### Renderer decision that needs a bounded experiment

The plan already acknowledges D3D9 state semantics and DX9 shader conversion. It nevertheless commits to a complete custom Vulkan backend before demonstrating the shader/content path. The reviewed plan mixed “MoltenVK gives macOS for free” and D3D9on12 “just works” with later corrections ([PORTING.md:2392](https://github.com/jm2/kisakcod/blob/5f29e810df88f0be323fccdc7d597c58e0d59f17/docs/PORTING.md#L2392)). The current plan replaces those assumptions with explicit experiments; these were conflicting guidance, not undiscovered risks.

Create an architecture decision with measured results before spreading renderer edits across the engine:

| Candidate | What to learn | Role in this plan |
|---|---|---|
| Existing D3D9 behind a small renderer boundary | Which resource/state operations the game actually needs; x86/x64 image and resource-lifetime baseline | Preserve as a reference during migration. |
| `dxvk-native` experiment | Representative retail SM3 shaders, constants, render targets and a scene under a native Linux process; compatibility and dependency costs | Optional bring-up aid or differential oracle. Changing it into the shipping endpoint would be an explicit plan decision. |
| Native Vulkan plus MoltenVK experiment | The same content on Linux and Apple Silicon, shader translation/cache behavior, resource synchronization and missing-feature fallbacks | Current intended endpoint; prove viability before the broad rewrite. |

The experiment should include skinning, transparent/alpha-tested materials, shadows/decals, postprocessing, resize/focus loss, shader compilation failure and warm/cold caches. Capture reference images and frame-time/memory measurements. Define a capability-oriented boundary rather than automatically cloning hundreds of individual D3D9 calls into a permanent wrapper API.

Specify shader policy explicitly: load original fast-files unchanged; identify bytecode by content hash; translate/cache without rewriting the user's retail archive; version the translator and cache format; regenerate from original inputs; reject unsupported programs clearly. An offline sidecar tool is possible, but its installation, mod compatibility and regeneration path must be part of delivery. Generated HLSL is not automatically a replacement for every retail or mod shader whose original source is unavailable.

Resolve the Windows ARM64 graphics decision in that same document. The milestone table still specifies D3D9on12 while the architecture calls for a shared Vulkan endpoint. Validate device creation, required import/dependency availability and VRAM/caps behavior on actual hardware. Do not forecast it as a cheap matrix extension until those checks pass.

### Lessons from earlier engine ports

These comparisons support the recommendation; they do not imply that KisakCOD can copy another engine's loader or cost estimate.

| Project | Evidence | Applicable lesson and limitation |
|---|---|---|
| ioquake3 | Its [README](https://github.com/ioquake/ioq3/blob/main/README.md) exposes separate server/client/renderer builds, SDL2, OpenAL, optional HTTP/codecs, and platform-specific writable data paths. Its [QVM interpreter](https://github.com/ioquake/ioq3/blob/main/code/qcommon/vm_interpreted.c) separates VM image offsets from host memory. | Deliver runnable engine slices, isolate platform/dependency choices, and keep compatibility observable. Its QVM model and original data formats differ from KisakCOD's decompiled native-pointer runtime and fast-files; adopting QVM is not a shortcut for the GSC VM. |
| OpenJK | Its [stated goals](https://github.com/JACoders/OpenJK/blob/master/README.md) prioritize backwards compatibility with existing games/mods and distinguish support by game and mode. | Publish explicit MP/SP/mod support instead of one platform checkbox. Preserve behavior and classify optional feature additions separately. Its existing cross-platform engine foundations do not solve COD4's D3D9/Miles/fast-file contracts. |
| dhewm3 | Its [README](https://github.com/dhewm/dhewm3/blob/master/README.md) describes a 64-bit port using SDL, OpenAL and CMake, documents required game-data versions, and links a mod support list/SDK. | Platform portability includes installation, data provenance, audio semantics and mod support. A shared library choice does not establish equivalence of the old audio behavior. |
| dxvk-native | Its [project documentation](https://github.com/misyltoad/dxvk-native) describes native Linux D3D9/11 use, replacement window integration and deployed game examples. | A native process can use a graphics translation library; Wine deployment and native integration are different options. Its documented Linux success is not proof of this game's Windows ARM64/macOS path. |
| MoltenVK | Its [runtime guide](https://github.com/KhronosGroup/MoltenVK/blob/main/Docs/MoltenVK_Runtime_UserGuide.md) documents SPIR-V conversion, caching, integration and limitations. | Probe Apple-specific renderer constraints early. Shared Vulkan code reduces duplication but does not eliminate platform QA or packaging work. |

ioquake3 also documents distinct current/legacy protocol settings and native64
module syscall-interface changes, while its QVM mods can run without native
recompilation. [ioquake3's developer documentation](https://github.com/ioquake/ioq3/blob/main/README.md#64bit-mods)
supports a useful design lesson for this fork: host ABI, mod image format and
network dialect need separate compatibility boundaries. This is an architectural
inference, not evidence that copying ioquake3's protocol settings or VM design
would make COD4 compatible. Both commercial COD4 references still need their own
production tests under #122/#127.

## Completion rules and next acceptance checkpoint

For each target, require progressively stronger evidence: configured → compiled → linked production executable → synthetic integration → licensed content startup → original-peer gameplay/compatibility → packaged clean-machine run. The mandatory compatibility stage is native client → both original servers and both original clients → native headless server, using the verified commercial 1.7 and Steam 1.8 references. A missing or unverified cell cannot pass. A utility artifact cannot advance the production rows. A hash library cannot advance actual graph parity until real walkers are enrolled. Tests with test-access authority cannot substitute for the corresponding production-macro composition.

Keep exact byte equality for valid disk/wire encodings and preserve original network semantics; normalize runtime graphs by semantic identity rather than pointer addresses. Define capture normalization only for explicitly identified session-dependent values without masking protocol or semantic differences. For simulation, define the compared state, initial conditions, tick schedule and RNG precisely. For rendering/audio, use documented scene- or signal-appropriate tolerances; those tolerances never relax network-visible compatibility. Resource/performance thresholds need reference hardware and a baseline, not an ungrounded percentage.

The next useful server checkpoint is **one native headless engine that loads a supported retail map, runs sessions with both verified original commercial 1.7 and Steam 1.8 clients, cycles maps, shuts down cleanly, and produces repeatable state/asset evidence**. This server checkpoint does not close the native-client → original-server direction or other platform cells. Keep reference/runner gaps pending while synthetic production integration proceeds. In parallel, prove representative retail shaders on the proposed graphics path. Those results will make remaining estimates substantially more credible than another increase in the utility-test count.
